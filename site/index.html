Green tests don't mean the spec is covered.

SpecTrace reads your requirements document, traces every numbered requirement to the code and tests behind it, writes the tests that are missing, and tells you what's covered, what's broken and what was never built, with evidence an auditor can check.

The problem

Traceability is still done by hand, in a spreadsheet.

Banks, insurers and healthcare teams must prove every requirement is implemented and tested before each release. Today someone reads the spec, searches the code for each requirement, checks for tests, writes the missing ones and updates a spreadsheet, then does it all again when the spec changes.

~30 min

per requirement to locate the code, find the tests, write what's missing and update the matrix. About 13.5 hours for a 27-requirement spec (our estimate).

Green ≠ covered

A passing suite only proves the existing tests pass. It says nothing about the requirements nobody tested.

Drift

When the spec changes and the code doesn't, nothing fails. The mismatch ships.

How it works

One command in Bob: /trace docs/requirements.pdf

  1. Start the clock

    Records the start time and pins a git baseline, so the tests Bob writes can never be mistaken for existing ones.

  2. Read the spec

    Document understanding pulls every requirement and acceptance criterion from the PDF, tables included, word for word.

  3. Trace in parallel

    One subagent per module finds the code, checks existing tests, writes missing JUnit tests, runs them and diagnoses failures.

    accountstransfersloanssecurity

  4. Verify

    A clean full test run, then a script rebuilds every status from the real results, not from what the agents said.

  5. Report

    A traceability matrix, a Markdown copy for PRs and a brief: bugs with file:line, gaps, tests added.

Then /fix patches the bugs and re-checks until the rows turn green, and /release-notes writes a release-readiness report. When the spec changes, /trace re-checks only the modules whose requirements changed.

Why trust it

The AI doesn't grade its own homework.

Agents can claim "all covered". SpecTrace doesn't take their word for anything that ends up in the report.

Statuses come from real test results

Every verdict is rebuilt from the Surefire XML the test run produced, and from the @Tag("REQ-…") annotations in the test source.

Disagreements are flagged

If a subagent says "covered" but its test fails, the report says so. The same goes for tests that are untagged or never ran.

Line numbers are checked

Every file:line an agent cites must exist and sit inside the method it names. Stale or invented locations are flagged.

Production code is off limits

Tracing modes can only write tests and reports. Only the separate Fixer mode may touch production code, and it may never weaken a test.

Run it

git clone https://github.com/decentkiwi/spectrace.git
cd spectrace && pip install -r tools/requirements.txt

You need JDK 21+, Python 3 and IBM Bob with the spectrace folder open as the workspace.

# baseline: the app's own tests, all green
cd bank-app && ./mvnw test

# in Bob
/trace docs/requirements.pdf       # trace all 27 requirements
/fix                               # patch the bugs, re-check, rows turn green
/release-notes v1.0.0              # release-readiness report
/trace docs/requirements-v2.pdf    # spec change: only Loans is re-checked

Results land in spectrace-out/matrix.html.
